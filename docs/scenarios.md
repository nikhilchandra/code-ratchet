# Scenarios

Each heading is one start-to-finish path through ratchet. The steps name the functions on the path in the order they run. The "Tests:" line names the tests that run the path from its entry function to its last step, or says "none yet". Where a test covers only part of a path, the line says which part.

## ratchet init

1. `ratchet.cli.main` sends the command to `ratchet.cli.run_init`, which asks the owner questions only when there is a terminal.
2. `ratchet.init_project.init_project` refuses a folder that is not a git repository or has uncommitted changes.
3. `ratchet.init_project._write_templates` writes config.toml and rules.md, never over a file that exists.
4. `ratchet.records.init_records` makes .ratchet its own repository.
5. `ratchet.init_project._add_ignore_line` adds .ratchet to .gitignore and commits it, after moving a project that tracks .ratchet with the owner's consent. The question and the "stopped tracking" line say how to restore the files.
6. `ratchet.records.commit_records` makes the first records commit.

## The first audit

1. `ratchet.cli.run_audit` loads the project with `ratchet.project.load_project` and calls `ratchet.audit.audit_run.start_audit`.
2. `ratchet.audit.audit_run.start_audit` takes the graph lock with `ratchet.graph_lock.take_lock`, which refuses while another graph runs or an audit waits, and refuses while rules.md is the template, or before init, and builds the graph with `ratchet.audit.audit_graph.build_audit_graph`. It releases the lock unless the audit waits.
3. `ratchet.audit.audit_graph.build_audit_graph.prepare` checks for a clean tree and an ignored .ratchet, writes the code findings and the inventory. A toml block in rules.md that `ratchet.target_design.read_target_design` cannot read, stops the audit, and `ratchet.cli.run_audit` prints one `ratchet: ...` line and exits with 1.
4. `ratchet.audit.audit_graph.build_audit_graph.audit` asks the auditor, and `ratchet.audit.audit_graph.build_audit_graph.review` asks list reviewers A and B together. Every agent turn is checked, and one that passes --output to git halts the audit.
5. `ratchet.audit.audit_graph.build_audit_graph.group` makes items, groups them, and asks the pair judge about the pairs that rules cannot settle.
6. `ratchet.audit.audit_graph.build_audit_graph.check_citations_step` fixes or removes citations that do not match the code.
7. `ratchet.audit.audit_graph.build_audit_graph.questions` writes questions.md and the job waits. `ratchet.audit.audit_run._answer_questions` collects answers with `ratchet.owner_terminal.ask_questions`, or resumes with none when there is no terminal.
8. `ratchet.audit.audit_graph.build_audit_graph.check` asks the checker, applies its verdicts and checks the citations again. It halts with an `AuditError` when the code moved while the job waited.
9. `ratchet.audit.audit_graph.build_audit_graph.draft` gives out ids and writes draft.md, then the job waits. `ratchet.audit.audit_run._approve_draft` shows the draft with `ratchet.owner_terminal.review_draft`, or the owner runs `ratchet audit --approve`, which calls `ratchet.audit.audit_run.settle_audit`.
10. `ratchet.audit.audit_graph.build_audit_graph.publish` checks the draft with `ratchet.audit.list_markdown.check_draft` against `ratchet.audit.audit_graph.done_ids`, writes the list, seeds its ledger with `ratchet.refactor.ledger.save_ledger`, adds settled rules to rules.md, and commits with `ratchet.records.commit_records`, which refuses a .ratchet that is not its own repository. `settle_audit` refuses to approve before that when the records repository is missing or damaged, and still lets the owner discard.

## A re-audit

1. `ratchet.audit.audit_run.start_audit` builds the graph as for a first audit. `ratchet.audit.audit_graph.build_audit_graph.prepare` finds an existing list with `ratchet.refactor.problem_list.find_problem_lists`, so the audit is a re-audit.
2. `prepare` works out when the old list was published with `ratchet.problem_history.publish_time`, and writes evidence hints with `ratchet.audit.evidence_hints.build_evidence_hints`. It also looks for .ratchet in the whole git history with `ratchet.audit.audit_graph._oldest_ratchet_commit`.
3. `ratchet.audit.audit_graph.build_audit_graph.audit` runs `ratchet.audit.audit_graph.build_audit_graph.audit_again`, which asks F, the blind audit, and R, the rechecker, together with `ratchet.agent_calls.ask_together`, and F is given no list, ledger or earlier answer. When .ratchet is found in the history, the auditor runs in F's place and `ratchet.audit.audit_run.start_audit` shows the note.
4. `audit_again` rejects a blind audit that touched paths outside the project, and asks R again for old ids that have no usable citation or subject. An auditor that stands in for F is held to the same rule, and every audit agent's file tools are confined to the project by where a path really is, so a short name, a link into .ratchet or a read outside the project is refused and the turn's log is checked for any call that got through.
5. `ratchet.audit.audit_graph.build_audit_graph.group` merges F's findings with R's checks of the old problems. `ratchet.audit.grouping.finish_groups` keeps only its own item in a group whose old problem is done or gone, and the other items come back as a new group for the checker.
6. `ratchet.audit.audit_graph.build_audit_graph.check_citations_step` and `ratchet.audit.audit_graph.build_audit_graph.check` run as in a first audit. The checker marks the entries that continue an old problem.
7. `ratchet.audit.audit_graph.build_audit_graph.draft` keeps an old problem's id and sets its status, such as reopened or blocked. `ratchet.audit.list_markdown.render_draft` lists the done and gone problems under Done, and records that the audit was not blind.
8. `ratchet.audit.audit_graph.build_audit_graph.publish` seeds the new ledger with a carried event for each carried problem, then a reopened or abandoned event where the status says so, and commits the records.

## A problem marked done by refactor, then reopened by a re-audit

1. A refactor run commits a job, and `ratchet.refactor.ledger.record_job` marks the problem done in the ledger of its list.
2. A later re-audit follows the re-audit path above, and the draft gives the problem the status reopened.
3. `ratchet.audit.audit_graph.build_audit_graph.publish` keeps its id and writes carried and reopened events in the new ledger.
4. `ratchet.problems_view.show_history` reads the problem's events from both lists as one timeline, through `ratchet.problem_history.problem_history`.

## A refactor run

1. `ratchet.cli.main` loads the project with `ratchet.project.load_project` and calls `ratchet.refactor.job_loop.run_refactor`.
2. `ratchet.refactor.job_loop.run_refactor` takes the graph lock with `ratchet.graph_lock.take_lock`, which undoes and halts a refactor that stopped without a word, then refuses a tree with changes, and runs the suite once with `ratchet.pytest_runner.run_pytest`. It asks `ratchet.pytest_runner.has_pytest_cov` whether coverage can run, and says once "coverage is not checked" when it cannot.
3. It finds the newest list with `ratchet.refactor.problem_list.find_latest_problem_list` and loads the ledger with `ratchet.refactor.ledger.load_ledger`.
4. For each job it starts the graph from `ratchet.refactor.job_graph.build_job_graph`. `ratchet.refactor.job_graph.build_job_graph.plan` asks the planner for one step, which names the functions, classes and module code it changes (as `package.module.qualname` and `package.module.<module>`), and the job ends there if the planner has nothing left.
5. `ratchet.refactor.job_graph.build_job_graph.super_plan` builds the pathway map of those functions with `ratchet.pathways.build_map`, lists the names the plan adds or moves to as new with `ratchet.pathways.describe`, and asks the super-planner. A revise goes back to plan at most `ratchet.refactor.settings.Caps.revisions` times, and an approve goes to write-tests or implement.
6. `ratchet.refactor.job_graph.build_job_graph.write_tests` asks the test writer for the listed tests, and `ratchet.refactor.written_tests.find_write_faults` refuses any change but a new passing test file. A refused write is undone with `ratchet.git.Repo.undo` and goes back a capped number of times.
7. `ratchet.refactor.job_graph.build_job_graph.implement` asks the implementer to make the change.
8. `ratchet.refactor.job_graph.build_job_graph.check_map` maps the functions the diff changes with `ratchet.pathways.functions_of_diff`, so a deleted function is named and not its neighbor. Any function, class or module code (`package.module.<module>`, for lines outside every function and class) outside the plan, outside the names the plan adds or moves to, and outside the ones already approved goes to `ratchet.refactor.job_graph.build_job_graph.review_map`, which asks the super-planner with `ratchet.refactor.agent_answers.MapReview`; an approve goes on and a revise goes back to implement as a rejection.
9. `ratchet.refactor.job_graph.build_job_graph.check_rules_step` runs `ratchet.refactor.rule_checks.check_rules` on the change, which also puts back any written test that the implementer changed, renamed or deleted.
10. `ratchet.refactor.job_graph.build_job_graph.test` runs the suite and compares it with the baseline. When coverage is on, `ratchet.pytest_runner.find_untested_lines` lists added src lines that no test runs, skipping files the coverage config omits (`ratchet.pytest_runner.read_coverage_omit`, `ratchet.pytest_runner.is_omitted`), and these lines go back to implement like a test failure.
11. `ratchet.refactor.job_graph.build_job_graph.review` asks the reviewer. An accept goes on, with comment fixes through `ratchet.refactor.job_graph.build_job_graph.fix_comments` first, and a reject goes back to implement.
12. `ratchet.refactor.job_graph.build_job_graph.commit` commits the change, with the written tests.
13. `ratchet.refactor.ledger.record_job` and `ratchet.refactor.ledger.save_ledger` record the job, and `ratchet.refactor.job_loop.run_refactor.save_records` commits the ledger with `ratchet.records.commit_records` when the run ends.
14. `ratchet.refactor.job_loop.run_refactor.end_run` counts the commits since the list was published, and suggests `ratchet audit` when the committed jobs reach `ratchet.refactor.job_loop.REAUDIT_JOBS`.

## A refactor job that halts

1. A step raises, such as an agent that gives no answer.
2. `ratchet.refactor.job_loop.run_refactor` catches it, even Ctrl-C, calls `ratchet.git.Repo.undo` if the tree has changes, marks the job halted with `ratchet.graph_lock.halt_job_file`, and releases the lock with `ratchet.graph_lock.release_lock`.
3. The ledger keeps the job_started events that `ratchet.refactor.job_graph.build_job_graph.plan` saved, so the problem stays open.
4. `ratchet.refactor.job_loop.run_refactor.save_records` commits the ledger, and the error is raised again.
5. `ratchet.cli.main` prints it on one line and returns 1.

A job that reaches a cap does not halt: `ratchet.refactor.job_graph.build_job_graph.undo` undoes it with `ratchet.git.Repo.undo`, the job ends abandoned, and the run goes on.

## ratchet reopen

1. `ratchet.cli.main` sends the command to `ratchet.cli.run_reopen`, which loads the project and calls `ratchet.reopen.reopen_problem`.
2. `ratchet.reopen.reopen_problem` refuses a project with no records repository, an empty reason, no list, or an id that is not a problem on the newest list.
3. It finds the list with `ratchet.refactor.problem_list.find_problem_lists` and `ratchet.refactor.problem_list.split_entries`.
4. It loads the ledger, sets the problem open, clears its sendbacks and adds a reopened event by the owner.
5. `ratchet.refactor.ledger.save_ledger` saves the ledger and `ratchet.records.commit_records` commits it.
6. `ratchet.cli.run_reopen` prints which list changed.

Tests: tests/test_reopen.py::test_the_command_reopens_and_prints_errors_on_one_line (through `ratchet.cli.main`, to the printed line) and tests/test_reopen.py::test_reopening_commits_the_ledger_in_the_records_repository (through `ratchet.reopen.reopen_problem`, to the commit).

## ratchet problems and --history

1. `ratchet.cli.main` sends the command to `ratchet.cli.run_problems`, which refuses --history with no problem and --all with a problem.
2. With no id, `ratchet.problems_view.show_lists` prints the newest list, or every list with --all.
3. With an id, `ratchet.problems_view.show_problem` prints the entry from the newest list that holds it.
4. With --history, `ratchet.problems_view.show_history` calls `ratchet.problem_history.problem_history`, which follows carried_from back through the older lists.
5. `ratchet.problems_view.describe_event` words each event, and `ratchet.cli.run_problems` prints the text.
